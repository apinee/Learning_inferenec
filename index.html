Stage 01 · Built so far

Tensors, precision and memory

phase1_foundations.py

The layout every script uses

Covered

Activations inside a transformer have the shape [batch, sequence length, hidden size]. Batch is how many requests run together, sequence length is how many tokens each has, and hidden size is the length of each token's vector (1024 for Qwen3-0.6B). Attention later splits the last dimension into heads, giving [batch, heads, seq, head_dim].

Why an inference engineer cares: batch and sequence length are the two numbers a serving system changes at runtime. Almost every speed and memory question comes back to how those two dimensions grow.

Linear projections are matrix multiplies

Covered
Y = X @ W.T X: [B, S, in] W: [out, in] Y: [B, S, out]

Query, Key, Value, the attention output and the three MLP projections are all this one operation. Over 95% of the weights in Qwen3-0.6B sit in these matrices. Your script checks the manual multiply against F.linear, which is the right habit: test each handwritten piece against a reference.

Why it matters: each generated token must read every one of these weight matrices from memory. That single fact explains why decoding is slow, and why quantization and batching help (stage 05).
Instrument 1 · Weight memory

Memory for the weights alone is parameters times bytes per parameter. The default is Qwen3-0.6B: 596M parameters with the embedding shared by the LM head.

Safe loading and the shape of Qwen3

Safetensors instead of pickle

Covered

.bin and .pt checkpoints are Python pickles, and loading a pickle can run any code its author put in it (CWE-502). Safetensors files hold only a JSON header and raw tensor bytes, so loading runs nothing, and the bytes can be memory-mapped without copying. With trust_remote_code=False, the model class also comes from the installed transformers library instead of the model repo.

Why it matters: serving systems load third-party weights all day. Knowing the format is also the first step to writing your own loader in stage 03, where you read tensors by name straight from the safetensors file.

Stage 02 · Built so far

RMSNorm and your first profile

RMSNorm.pyperfetto.py

RMSNorm

Verified against Hugging Face
y = x * rsqrt(mean(x²) + eps) * weight

RMSNorm rescales each token's vector to a steady size without subtracting the mean, which is cheaper than LayerNorm and works as well. Each Qwen3 layer runs it twice (before attention and before the MLP), plus once after the last layer. Your version matches Hugging Face to within 1e-5.

Why it matters: RMSNorm does very little maths per byte it reads, so it is limited by memory speed, not compute. It is the classic first kernel to fuse (stage 07), and your profile already shows it as three separate operations: square-and-mean, rsqrt-multiply, and scale.

Reading a profiler trace

Covered

perfetto.py warms up, labels regions with record_function, and exports a trace for ui.perfetto.dev. The warm-up and labelling are what professionals do. What to look for next time: how many separate operations each RMSNorm launches, how long the gaps between them are, and how the custom version compares with the library one at the same shape.

Stage 02 · Built so far

Attention

test_attention.py

Scaled dot-product attention

Covered
scores = Q @ K.T / sqrt(head_dim) weights = softmax(scores) output = weights @ V

Each token asks a question (its Query), every token offers a label (its Key), and the match between them decides how much of each token's content (its Value) to mix in. Dividing by the square root of the head size keeps scores from growing with vector length, which would make the softmax pick one token and ignore the rest.

Instrument 2 · Your test_attention.py, live

The keys and values are the ones in your script: "The" = [1, 0], "cat" = [0, 1], "milk" = [1, 1]. Change the query and watch the weights shift.

[1.0, 1.0]query
[7.52, 10.00]attention output

At the default query the weights are 0.248, 0.248 and 0.504, the same numbers your script prints. Turn off scaling and push the query to 3 to see the softmax collapse onto one token.

Stage 02 · Built so far

The causal mask

test_causal_mask.py

No looking ahead

Covered

A language model predicts the next token, so token i may only attend to tokens 0 to i. Setting future scores to −inf before the softmax makes their weights exactly zero. torch.triu(..., diagonal=1) builds that upper-triangle mask.

Rows are queries, columns are keys. Blue cells are allowed, red cells are masked.

Look at the last row. During generation you only ever compute that row, for the newest token, and it may attend to everything before it. That observation is the whole idea behind the KV cache in stage 04: the earlier rows' keys and values never change, so you store them instead of recomputing them.

Stage 02 · Built so far

Multi-head attention and grouped-query attention

test_multihead.pytest_gqa.py

Heads, then sharing heads

Covered

Multi-head attention runs several smaller attentions side by side, each with its own projection slice, so different heads can track different relationships. The heads are concatenated and mixed by o_proj.

Grouped-query attention (GQA) keeps many query heads but fewer key/value heads. Several query heads read the same K and V. Your script repeats K and V with repeat_interleave so the shapes line up, which is exactly what Hugging Face's repeat_kv does.

Instrument 3 · Who shares with whom
2×smaller KV cache than full multi-head
GQAattention type

Qwen3-0.6B is the default: 16 query heads, 8 KV heads. One KV head is called multi-query attention (MQA); equal counts is plain multi-head attention (MHA).

Why it matters: GQA exists for inference. Training cost barely changes, but the KV cache that every serving system stores per token shrinks by the sharing factor. Fewer bytes per token means more users fit in memory and each decode step reads less.
Stage 02 · Built so far

Rotary position embeddings (RoPE)

test_rope_basic.pytest_rope_positions.pytest_rope_frequencies.pyinspect_rope_config.py

Position as rotation

Frequencies coveredLayout match open
freq_i = theta^(-2i / head_dim) i = 0 … 63 angle = position × freq_i [a, b] → [a·cos − b·sin, a·sin + b·cos]

Attention alone cannot tell token order. RoPE rotates each pair of dimensions in Q and K by an angle proportional to the token's position. When two rotated vectors are compared with a dot product, only the difference in their angles survives, so the score depends on how far apart the tokens are, not on where they sit.

Instrument 4 · One pair spinning

Your vector [3, 4], rotated with Qwen3's real settings (theta 1,000,000, head dimension 128).

1.000radians per token for this pair
57.3°angle at this position
6.3tokens for one full turn
[−1.75, 4.69]rotated vector

Pair 0 turns a full radian per token and repeats every 6 tokens, so it encodes fine, local order. Pair 63 needs about 5 million tokens for one turn, so it changes very slowly and encodes long-range order. See review note 1: the README states this the other way round.

Code review

Review notes on the repo

The work is careful: every handwritten piece is checked against a reference, model loading is safe, and the README explains each step. These notes are what to fix before stage 03, roughly in order of importance.

Wrong fact

The README has RoPE's slow and fast pairs reversed

README section 4 says early pairs spin slowly and later pairs spin faster. With freq = theta^(-i/head_dim), pair 0 has frequency 1.0 (the fastest) and the last pair about 1.2e-6 (the slowest). Your own script prints this: the first frequency is exactly 1. Early pairs carry local order; later pairs carry long-range order. An interviewer reading the README would catch this.

Will break on real weights

Qwen3's head dimension is not hidden size ÷ heads

test_multihead.py and test_gqa.py compute head_dim = hidden_dim // num_heads. For Qwen3-0.6B that gives 64, but the real value is 128, so q_proj maps 1024 to 2048 and o_proj maps 2048 back to 1024. Read config.head_dim and size the projections from it.

head_dim = cfg.head_dim                                   # 128, not 1024 // 16
q_proj = nn.Linear(cfg.hidden_size, cfg.num_attention_heads * head_dim, bias=False)   # 1024 -> 2048
k_proj = nn.Linear(cfg.hidden_size, cfg.num_key_value_heads * head_dim, bias=False)   # 1024 -> 1024
o_proj = nn.Linear(cfg.num_attention_heads * head_dim, cfg.hidden_size, bias=False)   # 2048 -> 1024
Missing piece

Qwen3 normalises Q and K before RoPE (QK-norm)

Qwen3's attention has two extra RMSNorms, q_norm and k_norm, applied to each head's 128-dim vector after projection and before the rotation. Printing layers[0].self_attn in inspect_qwen3.py shows them. Your attention will not match Hugging Face without them, and the README's "what is still open" list does not mention them. Good news: your RMSNorm class already does the job.

q = q_proj(x).view(B, S, n_q, head_dim)
q = q_norm(q).transpose(1, 2)       # RMSNorm over head_dim, per head
k = k_norm(k_proj(x).view(B, S, n_kv, head_dim)).transpose(1, 2)
q, k = apply_rope(q, k, cos, sin)     # rotation comes after the norm
Known gap

Match the rotate_half layout

You spotted this one in the README: your script pairs dimension 0 with 1, while Hugging Face pairs dimension j with j + 64. Same frequencies, different layout. Switch to the half-split form and the rotated vectors will match exactly.

def rotate_half(x):
    x1, x2 = x[..., : x.shape[-1] // 2], x[..., x.shape[-1] // 2 :]
    return torch.cat((-x2, x1), dim=-1)

freqs = torch.outer(positions, inv_freq)          # [S, 64]
emb = torch.cat((freqs, freqs), dim=-1)          # [S, 128]: same angle for j and j+64
q_rot = q * emb.cos() + rotate_half(q) * emb.sin()
Precision

RMSNorm only matches in FP32

Hugging Face's RMSNorm converts the input to FP32, normalises, converts back, then multiplies by the weight. Your version stays in the input dtype. That is identical in FP32, but in BF16 the results will drift. Copy the upcast before you move to BF16.

def forward(self, x):
    dtype = x.dtype
    x = x.float()
    x = x * torch.rsqrt(x.pow(2).mean(-1, keepdim=True) + self.eps)
    return self.weight * x.to(dtype)
Your hardware

Device detection only knows CUDA

phase1_foundations.py, phase2_load_model.py and perfetto.py check torch.cuda and otherwise fall back to CPU, so your Intel GPU is never used. PyTorch exposes Intel GPUs as xpu. Put one helper in a shared module and use it everywhere, including the profiler.

def pick_device() -> str:
    if torch.cuda.is_available(): return "cuda"
    if hasattr(torch, "xpu") and torch.xpu.is_available(): return "xpu"
    return "cpu"

def sync(device):                   # call before reading a timer
    if device == "cuda": torch.cuda.synchronize()
    elif device == "xpu": torch.xpu.synchronize()

Steps, in order

class MLP(nn.Module):
    def __init__(self, d=1024, f=3072):
        super().__init__()
        self.gate_proj = nn.Linear(d, f, bias=False)
        self.up_proj   = nn.Linear(d, f, bias=False)
        self.down_proj = nn.Linear(f, d, bias=False)
    def forward(self, x):
        return self.down_proj(F.silu(self.gate_proj(x)) * self.up_proj(x))

Not startedMost important concept in the field

KV cache, prefill and decode

Keys and values for past tokens never change, so you store them. Generation then has two phases. Prefill processes the whole prompt in one pass: large matrix multiplies, limited by compute, and it sets the time to first token (TTFT). Decode produces one token per step, reusing the cache: small multiplies that must still read every weight, limited by memory bandwidth, and it sets the time per output token (TPOT).

KV bytes per token = 2 (K and V) × layers × kv_heads × head_dim × bytes per value
Instrument 5 · KV cache size
112 KiBper token
448 MiBper request at this context
3.50 GiBfor all requests

Defaults are Qwen3-0.6B. With 8 requests at 4k context the cache is about three times the size of the BF16 weights. On long contexts the cache, not the model, is what fills memory.

Build: a preallocated cache tensor per layer, separate prefill() and decode_step() functions, and a benchmark script that records TTFT, TPOT and tokens per second to JSON. Plot naive against cached generation.

Interview check: Your model has 28 layers, 8 KV heads of size 128, and stores the cache in BF16. How much memory do 32 users at 8k context need? (About 28 GiB.)

Stage 05

Performance on real hardware

Not started

Memory bandwidth and the roofline

Every operation does some maths (FLOPs) and moves some bytes. Their ratio, the arithmetic intensity, decides whether the chip waits on memory or on compute. A decode step at batch size 1 does about 2 FLOPs per weight while reading 2 bytes per weight: intensity near 1, far below what any GPU needs to stay busy. That is why batching raises throughput almost for free: 16 users share one read of the weights.

Instrument 6 · Decode speed floor

The fastest possible decode at batch size 1 reads all weights once per token. Measure your real bandwidth with a large tensor copy and put it here.

17.0 msper token, at best
59tokens per second, at best

100 GB/s is a rough figure for a laptop with shared memory; an Arc discrete card is several times higher. If your measured TPOT is far above this floor, the time is going to overhead such as Python, kernel launches or extra copies.

  • Profile the full forward pass and sort operations by time: expect the linear layers to dominate decode and attention to grow with context.
  • Learn what the profiler shows on XPU, and why you must synchronise before reading a timer on any GPU.
  • Understand the hardware words: Xe cores and XMX matrix units on Intel; SMs and tensor cores on NVIDIA; on-chip SRAM against main memory (HBM or GDDR).
Build: bench/bandwidth.py that measures GB/s on your device, then compare your stage 04 TPOT with the floor and explain the gap in the README.
Stage 06

Serving systems

Not started

Continuous batching

Static batching waits for the longest request and pads the rest. Continuous batching, from the Orca paper, rebuilds the batch at every decode step: finished requests leave, waiting ones join. A scheduler keeps waiting, running and finished queues and decides who runs next.

Build: a scheduler and engine loop that serve requests of different lengths together, plus a load generator. Plot throughput against concurrent users.
Not started

Paged KV cache

Reserving a full-length cache per request wastes most of it. PagedAttention (the vLLM paper) splits the cache into fixed-size blocks, like operating-system memory pages, with a block table per request. Blocks are allocated as tokens arrive and freed when a request ends.

Build: a block manager with reference counts, and attention that reads K and V through the block table. Report how many more requests fit.
Not startedGood fit for agent work

Prefix caching

Many requests start the same way: a system prompt, tool definitions, earlier turns of a chat. SGLang's RadixAttention keeps cached blocks in a radix tree keyed by token sequence, so a new request reuses the longest matching prefix and only prefills the rest. Least-recently-used blocks are evicted first.

Build: a radix-tree cache and a synthetic agent trace with a shared 2k-token system prompt. Measure TTFT with and without it. This is the strongest single result you can put on a resume.
Not started

Chunked prefill and preemption

A long prompt can stall every other user's decode. Chunked prefill splits it into pieces that share steps with decoding requests. When memory runs out, the scheduler preempts a request and either swaps its cache out or recomputes it later.

Build: chunked prefill with a token budget per step; measure p99 TPOT while a long prompt arrives.

Interview check: Why does continuous batching help throughput but can hurt the latency of an individual request? What does chunked prefill trade?

Stage 07

Kernels

Not started

Why kernels, and which ones

  • Fusion. Your RMSNorm profile shows three operations, each reading and writing the whole tensor. One fused kernel reads once and writes once. The same applies to RoPE, SiLU-times-up, and residual-plus-norm.
  • FlashAttention. Computes attention in tiles held in fast on-chip memory, with a running (online) softmax, so the full sequence-by-sequence score matrix is never written out. Prefill gets much faster and memory drops from quadratic to linear in sequence length.
  • Paged decode attention. Reads K and V through a block table for many requests at once. This is the kernel behind stage 06.
  • Launch overhead. At batch size 1, a decode step is hundreds of tiny kernels; the gaps between them can cost more than the maths. torch.compile and graph capture remove much of it.

Tools on your Intel GPU

  • Triton lets you write GPU kernels in Python. Intel's XPU backend for Triton is bundled with recent PyTorch XPU builds, so the same kernel source runs on Intel and NVIDIA.
  • torch.compile generates fused Triton kernels for you on XPU. Start here and read the code it produces.
  • SYCL is Intel's C++ GPU language, used by llama.cpp's Intel backend. Worth reading, not required to start.
Build: a fused RMSNorm in Triton, tested against your PyTorch version; then torch.compile on the decode step with a profile before and after. Stretch: a simple tiled attention kernel with online softmax.

Interview check: Walk through the online softmax trick. How can you compute softmax over a row you only see one tile at a time?

Stage 08

Quantization

Not started

Storing weights in fewer bits means fewer bytes per decode step, and decode speed tracks bytes read. Instrument 1 shows the memory effect: Qwen3-0.6B drops from 1.19 GB in BF16 to about 0.3 GB in INT4.

  • Scales. w ≈ scale × int_value. Per-tensor, per-channel and group-wise scales (one scale per 32 to 128 weights) trade accuracy against overhead.
  • Weight-only quantization (INT8 or INT4 weights, BF16 maths) helps decode most. Weight and activation quantization (W8A8, FP8) also speeds up prefill on hardware with low-precision matrix units.
  • GPTQ and AWQ quantize after training using a small calibration set, choosing roundings or scales that protect the weights that matter most.
  • KV cache quantization (FP8 or INT8) halves instrument 5's numbers and fits twice the users.
  • Measure quality. Perplexity on held-out text and a small task evaluation before and after. A fast model that answers worse is not a win.
Build: your own INT8 weight-only linear layer with per-channel scales; a table of memory, TPOT and perplexity for BF16 and INT8. Stretch: INT4 through torchao, which supports Intel GPUs.

Interview check: Why do outliers in activations make INT8 activation quantization hard, and what do methods like SmoothQuant do about it?

Stage 09

Decoding algorithms

Not started

Speculative decoding

Decode is limited by reading weights, so checking 5 tokens costs about the same as producing 1. A cheap draft proposes several tokens; the main model verifies them in one pass and keeps the longest accepted run. A rejection-sampling rule keeps the output distribution identical to the main model's.

  • Draft from a smaller model of the same family (Qwen3 has several sizes).
  • Prompt lookup: draft by copying n-grams from the prompt. No second model; good for summarising and for agents quoting tool output.
  • Know the names: Medusa heads, EAGLE.
Build: prompt-lookup speculation with acceptance rate and speedup reported.
Not started

Constrained and structured output

Turn a JSON schema or grammar into a state machine and, at every step, mask the logits of tokens that would break it. The model can then only produce valid JSON tool calls. Libraries such as Outlines and XGrammar do this efficiently by precomputing which tokens are allowed in each state.

Build: schema-constrained tool calls on your engine; report the share of valid outputs with and without the mask, and the per-token cost of masking.
Stage 10

Scale and long context

Not startedMostly theory on one GPU
  • Tensor parallelism. Split each weight matrix across GPUs; all GPUs work on every token and exchange partial results (all-reduce) twice per layer. Needs fast links between GPUs.
  • Pipeline parallelism. Put different layers on different GPUs; requests flow through like an assembly line. Less communication, more latency.
  • Mixture of experts and expert parallelism. Many MLPs ("experts") per layer, with a router choosing a few per token. Total parameters are large but each token uses a small part. Experts are spread across GPUs. Qwen3 has MoE variants worth reading.
  • Disaggregated serving. Run prefill and decode on separate machines, because one is compute-bound and the other memory-bound, and move the KV cache between them.
  • Long context. Stretching RoPE beyond the training length (position interpolation, NTK scaling, YaRN). Your inspect_rope_config.py already prints rope_scaling; this is what that field controls. Also sliding-window attention and why long contexts make attention, not the MLP, the bottleneck.
  • Multi-LoRA serving. One base model with many small fine-tuned adapters swapped per request.

Interview self-check

Answer out loud first, then open the hint.

Why is decoding memory-bound and prefill compute-bound?

Decode multiplies one token's vector by every weight matrix, so each weight byte loaded supports about one multiply-add. Prefill multiplies hundreds of tokens by the same weights, so each byte loaded is reused hundreds of times and the matrix units become the limit.

Compute Qwen3-0.6B's KV cache per token in BF16.

2 × 28 layers × 8 KV heads × 128 × 2 bytes = 114,688 bytes, about 112 KiB. Without GQA (16 KV heads) it would be twice that.

What does GQA change, and what does it cost?

Fewer KV heads shrink the cache and the bytes read per decode step by the sharing factor. The cost is a small loss of model quality, which training largely recovers.

Why does RoPE make attention depend only on relative position?

Rotating q by angle mθ and k by nθ makes their dot product depend on (m − n)θ, because rotations compose by subtracting angles inside the dot product.

Why does batching raise throughput nearly for free during decode?

All requests in the batch share one read of the weights. Until the batch is large enough to become compute-bound, adding users adds little time per step.

What problem does paged attention solve?

Fragmentation and over-reservation in the KV cache. Fixed-size blocks allocated on demand mean memory is only used for tokens that exist, so more requests fit.

How does speculative decoding keep outputs identical to the main model?

Each drafted token is accepted with probability min(1, p_main / p_draft); on rejection, a token is sampled from the normalised difference of the two distributions. The result is distributed exactly as the main model's output.

Name three metrics you would put on an inference dashboard and why.

TTFT p99 (user-perceived responsiveness), TPOT p99 (streaming smoothness), and KV cache utilisation or queue depth (whether you are about to preempt or need to scale).
